# SLO V3

SLO использует существующие метрики workload `sdk.*`, исход процесса и проверки данных. `workload_type` выбирает операции: `table` (по умолчанию), `topic` или `topic_tx`. Табличный SLO обязательно сравнивает current с независимо собранным baseline.

## Таблицы

- **T01. Запись:** UPSERT под нагрузкой и отказами; подтверждённые значения проверяем чтением.
- **T02. Чтение:** SELECT подтверждённых ключей; сверяем данные, пустой ответ не считаем успехом.
- **T03. Восстановление:** после снятия отказа полезная нагрузка возвращается до deadline.
- **T04. Пул:** после отказа сессии восстанавливаются, запросы не зависают.

Метрики: `sdk.operations.total` с `operation_type`, `operation_status`, `ref` и `sdk.operation.latency.p50/p95/p99.seconds` для успешных логических операций. `deploy/metrics.yaml` сохраняет исходные запросы и сравнение current/baseline. Action требует успешные read/write-наблюдения обеих версий; ошибки процесса и существующие проверки данных дают FAIL.

## Топики

- **P01. Доставка:** все сообщения с ACK прочитаны, payload и порядок внутри партиции сохранены; после записи выполняем drain.
- **P02. Batch/single:** оба API проходят одинаковую проверку данных и commit.
- **P03. Commit retry:** после временной ошибки целевой offset подтверждён; допустимые повторы дедуплицируем.
- **P04. Зависший клиент:** общий поток не скрывает остановку отдельного Writer/Reader.
- **P05. Backpressure:** ожидание или отказ соответствует API; после снятия ограничения работа продолжается.
- **P06. Транзакции:** проверка атомарности таблицы и топика — следующий этап, текущий worker её не покрывает.

Topic-workload используют `workload_type: topic`, существующие `sdk.*` метрики и свои прежние YAML-запросы. Action требует успешные read/write-наблюдения текущего workload и baseline, если он задан. Ошибки процесса, существующие проверки данных и пороги сохраняются; тип workload не добавляет новые сценарии доставки.

Существующий Rust Topic-tx учитывает всю транзакцию как одну операцию `transaction`. Для него `workload_type: topic_tx` требует успешные транзакционные наблюдения вместо отдельных read/write; прежние workload-проверки атомарности и transaction YAML остаются без изменений. Наличие счётчика само по себе не добавляет доказательства commit.

## Вердикт

При миграции Action существующие метрики, процесс SLO и baseline сохраняем. Action проверяет наблюдения workload и исход процесса; JSON с проверками необязателен и оценивается, только если workload его уже формирует. Сценарии выше не требуют переписывания текущего workload.

**PASS:** данные корректны, нагрузка и восстановление в заданном бюджете. **FAIL:** нарушен инвариант или deadline. **INVALID:** сценарий не исполнен либо нет обязательных данных.

Порог, нагрузку и deadline задаём до запуска. Ошибка попытки не равна ошибке логической операции. Нет метрик — не ноль. Counter считаем через rate/increase; готовые latency-перцентили обрабатываем существующими Gauge-запросами.

Отказы: graceful stop, restart, SIGKILL, pause, rolling restart, network blackhole. Сохраняем параметры, итог проверок, метрики, логи и события отказов. Любая ошибка проверки должна дать ненулевой exit code.
